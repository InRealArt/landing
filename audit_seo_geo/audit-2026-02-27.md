### P1-4 — Plusieurs balises H1 par page (violation critique de hiérarchie)

**Fichiers :** `src/components/home/Intro.tsx:31`, `src/components/home/HowItWorks.tsx:29,34`, `src/components/home/Statistics.tsx:26,30`, `src/components/home/Explore.tsx:57`, et 20+ autres composants

La homepage seule possède 6+ `<h1>`. C'est l'une des erreurs SEO on-page les plus impactantes. Google et les LLMs utilisent la hiérarchie des titres pour comprendre la structure et le sujet principal d'une page.

**Exemples trouvés :**
```tsx
// Statistics.tsx:26 — titre de section en h1
<h1 className="text-4xl md:text-5xl">{t('home.statistics.title')}</h1>
// Statistics.tsx:30 — chiffres stats en h1
<h1 className="text-4xl lg:text-6xl">{stat.number}</h1>
// HowItWorks.tsx:29 — titre de section en h1
<h1 className="text-3xl lg:text-5xl text-center">{t('home.howItWorks.title')}</h1>
// HowItWorks.tsx:34 — titre de carte en h1
<h1 className="text-2xl lg:text-3xl">{item.title}</h1>
```

**Structure correcte pour la homepage :**
- Un seul `<h1>` : le titre héro principal (`home.intro.title`)
- `<h2>` pour chaque section : titre Statistics, "Comment ça fonctionne ?", etc.
- `<h3>` pour les cartes dans les sections : stats individuelles, titres how-it-works

**Modèle de correction (les classes Tailwind restent identiques) :**
```tsx
// Statistics.tsx — h1 → h2 pour le titre, h1 → p pour les chiffres
<h2 className="text-4xl md:text-5xl bricolage-grotesque">{t('home.statistics.title')}</h2>
<p className="text-4xl lg:text-6xl bricolage-grotesque font-semibold">{stat.number}</p>

// HowItWorks.tsx
<h2 className="text-3xl lg:text-5xl bricolage-grotesque text-center">{t('home.howItWorks.title')}</h2>
<h3 className="text-2xl lg:text-3xl unbounded overflow-hidden text-ellipsis">{item.title}</h3>
```

**Fichiers à mettre à jour :**
- `src/components/home/Statistics.tsx`
- `src/components/home/HowItWorks.tsx`
- `src/components/home/Explore.tsx`
- `src/components/roadmap/Roadmap.tsx`

### P1-5 — hreflang FR et EN pointent vers la même URL

**Fichiers :** `src/utils/metadata.ts` (lignes 47-52), `src/app/layout.tsx` (lignes 48-53)

```ts
// layout.tsx
alternates: {
  canonical: 'https://inrealart.com/',
  languages: {
    'x-default': 'https://inrealart.com/',
    'fr': 'https://inrealart.com/',
    'en': 'https://inrealart.com/',
  },
},
```

Le site utilise un switch de langue côté client (Zustand + localStorage). Google ne voit qu'une seule URL quelle que soit la langue, et les signaux hreflang FR et EN identiques sont contradictoires.

**Option A (recommandée — changement minimal) :** Supprimer l'alternate `en` puisqu'il n'existe pas d'URL distincte. Garder uniquement `x-default` et `fr`.

**Option B (SEO bilingue complet — refactoring important) :** Ajouter un routing URL par langue (`/fr/` et `/en/`) avec hreflang pointant vers des URLs distinctes.

**Correction immédiate pour `src/utils/metadata.ts` (Option A) :**
```ts
alternateLanguages = {
  'x-default': canonical || BASE_URL,
  'fr': canonical || BASE_URL,
  // 'en' supprimé — ne pas déclarer ce qu'on ne peut pas supporter avec des URLs séparées
}
```

## Score GEO et opportunités d'amélioration

### Score GEO actuel : 42/100

**Ce qui fonctionne :**
- Organisation + WebSite JSON-LD sur la homepage (SSR — lisible par les LLMs)
- Article JSON-LD sur les articles de blog via champ `jsonLd` en base (bon pattern)
- Person + VisualArtwork + BreadcrumbList sur les pages artistes (SSR — signaux d'entité forts)
- Section Statistics avec chiffres concrets et citables (35+ artistes, 600+ œuvres)
- Page Manifeste avec phrases déclaratives claires
- Composant FAQ présent sur presque toutes les pages

**Lacunes GEO critiques :**

1. **FAQPage schema rendu côté client** — Les LLMs ne peuvent pas extraire les Q&R. C'est le fix GEO au ROI le plus élevé (+40% de visibilité IA).

2. **Aucune page de contenu définitionnel** — Pas de page standalone pour "tokenisation d'art", "leasing artistique", "LOA pour les artistes". Ces pages seraient des cibles de citation LLM très performantes. Le glossaire existe mais est une SPA filtrée côté client.

3. **Statistics sans source** — Les chiffres homepage (35+ artistes, 600+ œuvres, 100% satisfaction) manquent d'attribution. Ajouter "au [date]" ou une source.

4. **Aucune biographie auteur en schéma** — Les articles ont un `author` mais pas de page `Person` dédiée pour chaque auteur avec leurs credentials. Des pages `/team/[slug]` individuelles amélioreraient dramatiquement l'EEAT.

5. **Contenu peu chunked pour les LLMs** — Restructurer les paragraphes clés en format "réponse d'abord" :
   - Avant : "InRealArt transforme le marché de l'art haut de gamme en offrant..."
   - Après : "InRealArt est une marketplace d'art sélective basée à Paris. Elle permet aux collectionneurs d'acheter, louer et investir dans des œuvres d'art contemporain avec traçabilité garantie."

6. **Pas de pattern `@graph`** — La homepage pourrait combiner Organization, WebSite, et ArtGallery dans un seul bloc JSON-LD `@graph` pour améliorer le parsing des relations d'entités par les LLMs.

## Analyse bilingue / hreflang

### Résumé architectural

InRealArt utilise une architecture **URL unique, switch de langue côté client** (Zustand + localStorage). Il n'existe pas de préfixe `/fr/` ou `/en/` dans les URLs.

### Implications SEO

| Signal | État actuel | Impact SEO |
|---|---|---|
| hreflang fr | Même URL que en | Pas de différenciation |
| hreflang en | Même URL que fr | Pas de différenciation |
| Attribut `lang` | Hardcodé `fr`, override JS | Les crawlers voient toujours `fr` |
| `og:locale` | `fr_FR` uniquement | OK pour audience FR |
| Article `inLanguage` | Défini par langue du post | Bien pour le blog |
| Structure URL | Sans langue | Ne peut pas ranker EN séparément |

**Conclusion :** Si l'objectif est d'attirer des collectionneurs et investisseurs anglophones, le routing URL par langue est nécessaire. Si le site cible principalement le marché français avec l'anglais en secondaire, l'architecture actuelle est acceptable — mais le hreflang `en` redondant doit être supprimé.
